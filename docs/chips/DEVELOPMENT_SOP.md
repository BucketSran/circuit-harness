<a id="development-workflow"></a>

## 开发工作流

从当前请求、Git 状态、所属组件和已有 Issue/PR 恢复任务。沿用已经确定的目标、测试边界、
依赖与授权；只有新证据改变判断时才重新讨论。小修和文档修改可以直接进入相应阶段。

Matt、pstack 共享 skills 提供方法，项目 skills 补充职责、兼容约束和证据要求。
从客户端实际技能目录读取正文，遵守调用设置；本仓库不复制整套共享技能，也不修改全局安装。

| 当前需要 | 使用入口 | 本阶段完成条件 |
| --- | --- | --- |
| 讨论目标、约束或验收 | 用户选定的 `grill-with-docs`；`grilling` 与 `domain-modeling` | 关键决定明确，写回所属文档或讨论记录 |
| 保存规格、拆分依赖 | 用户选定的 `to-spec`、`to-tickets` | 复用已有 [tracker](../agents/issue-tracker.md)，范围与验收可核查 |
| 实现行为 | `chips-dev`，按需使用 `implement`／`implement-spec` 与 `tdd` | 受影响行为及兼容性有实际验证 |
| 选择检查、执行验证、重分析 | `chips-dev` | 完成用户指定操作，区分既有证据与新执行 |
| 审查 | `review-pr` 适配共享 `code-review` | 分别核对规范与 spec，记录实际差异、问题和证据 |
| PR 与交付 | `prepare-contribution`，每次正文创建／更新使用 `pr`，再用 `unslop` | 满足下面的人工 review 或自主合并约定 |

共享默认步骤按本项目适配：复用已确认的测试入口；先从 PR/Git 解析真实 base/head；
按影响范围选择检查。文档工作不用模拟 TDD，“完整检查”不扩成其他领域的真实评测。
`implement-spec` 的单集成分支适用于确有耦合的工作，不覆盖本项目默认的 ticket/PR 粒度。
本项目允许每项行为在 Green 后立即整理并复测，无需等到 review 阶段才做 Refactor。
仅重分析保存证据时，不启动 `diagnosing-bugs` 的复现／修复循环；按现有证据区分观察、假设和未知，
把仍需执行的验证列为下一步，不将假设写成已确认根因。

按任务需要加载补充方法：共享接口变化用 `blast-radius`，测量性能用 `benchmark-checklist`，
有证据的重复错误用 `correct`，指令文档用 `writing-for-agents`，面向人的文档用 `technical-writing`。
实质多阶段或无人值守任务用 `show-me-your-work` 保存一份关键决策记录；其内容由共享 skill 维护，
不再增加另一种执行账本。

<a id="delivery-and-review"></a>

## PR、审查与交付

默认一个可独立验收的 ticket 对应一个 PR；足够小的 spec 可以直接作为交付单位。
每个 ticket 交付可验证的完整行为，测试与必要故障处理随行为交付。
只有多个改动必须共同形成可验证结果时，才共用一个集成 PR。依赖由实际契约决定，
不能把产品路线的先后顺序机械当作全部 ticket 的阻塞关系。

开发默认完成实现、相关检查、独立审查、必要修复、提交和 PR 发布，交给用户 review。
用户确认后继续合并到 `main` 并同步日常目录；明确要求“自主完成并合并”的任务，
在约定检查通过后直接完成整合，不重复询问。讨论、只读审查和仅拟稿请求停在各自阶段。
真实主机、模型和费用仍沿用具体任务的资源授权。

实质行为变更做一次独立 Standards／Spec 双视角审查，给审查者准确的基准、待审版本、
需求、相关文档和可访问证据。实现者核实问题，修复后检查并复查受影响部分。
小文档修改按风险做事实、链接和 diff 检查。相同版本、相同要求和相同证据的已完成审查可以复用；
新的改动、失败或未解决问题才触发追加审查。固定三轮模式仅用于明确要求的专项加固。

每次创建或更新 PR 正文，必须读取并使用共享 `pr`，通过
[prepare-contribution](../../.agents/skills/prepare-contribution/SKILL.md) 适配本仓模板。
交付说明让用户能查看改动目的、关键 diff、实际验证、兼容影响和未完成项。
长任务可链接经过检查且适合分享的决策记录；日志不替代 diff 或运行证据。

Review 修复留在同一 PR。合并前核对最新 head、检查与反馈；用户确认后新增的实质变化应再供 review。
合并后才发现问题时，根据影响选择修复 PR 或 revert，不重写共享历史。
远端执行等副作用不因代码回退自动撤销。

允许合入边界明确且兼容的实现，同时保留尚未完成的真实 Spectre／Agent 验收。
若缺少验证使现有路径正确性也无法判断，则不能把它当作可合入结果。
只关闭验收已经完成的 ticket；父 spec 尚有验收缺口时继续保持开放。
PR 应链接完整 spec，但只对完成的交付使用关闭关键字。

<a id="shared-backend-workflow"></a>

## 共享后端与跨仓库协作

跨仓库任务由一个聊天协调，显式识别 Harness 与调用方的实际 checkout。
修改前读取各仓 AGENTS、所属组件契约、相关技能和未提交改动。
先确定请求、结果、错误语义和验收条件：Harness 维护执行与证据回收；
vaEVAS 维护 EVAS 引擎语义和 benchmark 内容／评分，课程项目维护课程工程。
共享接口说明留在拥有者组件，调用方引用它。

同一工作区的写入、切分支和提交由一个负责人管理。并行任务先约定可写路径，重叠修改串行处理；
一个仓库的 worktree 不隔离另一个仓库。分别记录源码身份与未提交差异，除各自检查外核验完整调用链。
提交和 PR 各归所属仓库，注明版本依赖与合并顺序。一次任务集成不自动授权整合另一项工作。

<a id="workspace-handoff"></a>

## 工作区与交接

日常 checkout 是用户查看成果的入口；开始或恢复编辑时核对实际路径、分支、remote、
Git worktree 清单和未提交修改。复用合适的任务分支；新独立工作从已检查的 `origin/main`
建立 `codex/` 分支，只有真实依赖才从另一任务分支开始。保护私有参考备份和其他人的修改。旧私有 checkout 不得改接公开 remote；从它迁移改动时只转移已审查源码，不合并旧历史。

串行且无冲突的工作可以直接使用合适的 checkout。需要隔离时，临时 worktree 优先放在项目旁
可见的 `worktrees/` 目录；宿主管理工具使用其他位置时，在项目入口提供可见链接。
本地入口记录用途、分支、PR 和未整合原因，不把个人绝对路径写进 Git 或公开 PR。
原始主机配置和证据按各自权限保存；导航不替代访问控制。

交付明确区分已实现／已验证、已提交／发布 PR、已合入目标分支、日常目录已同步。
等待用户 review 时保留可访问的 PR 与工作区入口；合并不会自动更新另一份 checkout。
获准整合后先检查并协调日常目录的并发修改，再同步；不能以 reset 或覆盖方式抹掉它们。

退役前核对未提交文件、未推送提交、所需 ignored 材料及仍在执行的任务，先保留必要内容。
已有授权覆盖时完成收尾，否则报告具体保留原因。使用宿主管理的 worktree 时按其归档机制处理；
Git 管理的临时目录在确认可退役后通过 Git 移除。同步后更新可见入口。

本规则目前由 Agent 在开始和交接时执行。CI 看不到用户电脑上的其他 checkout，
也不能证明人工 review、实验授权或日常目录同步已经发生。

<a id="documentation-policy"></a>

## 文档入库与维护

仓库保存可复用、需要随代码维护的内容。计划制定中的草稿默认留在本地；
“写一份方案”不自动等于“将全部规划产物加入 Git 并上传”。

| 内容 | 默认位置与处理 |
| --- | --- |
| 未定稿计划、方案推演、临时执行清单 | 已被忽略的 `.planning/chips/`；不强制加入 Git，不为每轮讨论新增长期文档 |
| 需要协作的范围、问题、验收条件与进度 | 在当前授权范围内优先更新所属仓库的已有 Issue；公开 Issue 只写可分享的范围与结论 |
| 已确定的接口、使用方式、部署规范 | 更新现有 `docs/chips/` 对应文档；只有独立、持续维护的职责才新增文件 |
| 可复现实验条件与回归 | 无凭据的配置模板、任务定义、测试代码和安全夹具进入 `examples/chips/`、`tests/` 等所属位置 |
| 原始 prompt、模型轨迹、仿真日志／波形、实际主机配置 | 留在私有 `runs/` 或部署规范指定的存储；Git 忽略不代替目录权限与备份 |
| 有长期参考价值的调查结果 | 选择性保留经审查的精简结论、条件、限制与证据引用；优先更新现有验证记录，不复制完整运行产物 |

规划阶段不额外要求成套 plan／tracker／manifest 文件。用户明确要求版本化的方案可以入库，
但应标明草案状态、与现有文档的关系，并避免并行维护多份相同结论。
“小改动逐次 commit／push”适用于当前范围内的实际交付，不要求上传所有草稿或对话过程。
提交前只选择与本次交付有关的文件；不得用 force-add 绕过规划／证据目录的忽略规则。
已有文档的迁移或删除作为独立清理处理，不在普通修改中顺带进行。

准备公开源码时遵循[仓库发布边界](REPOSITORY_SCOPE.md#publication-boundary)：
提交通用代码、脱敏文档和安全夹具；真实实验档案与完整研发历史保持私有。
清理后从具体提交导出源码候选，检查实际包内容。PR 合并不自动授权公开仓库、发布数据或改写历史。

<a id="current-experiment-path"></a>

## 当前真实实验主线

按[接入指南](../guides/integration.md)选择任务执行路径。原生 Harbor 任务保留环境与 checker；
公开会话补充受控仿真、候选冻结与私有终评。Harbor 负责 Agent、Job 和 Trial，Agent 与 Model 分别配置。
runner 可以在本机或服务器；Pi 与 GLM 的服务器运行不要求本地 Codex 参与。

任务判据归 benchmark，EVAS 算法归 vaEVAS，执行与证据归 Harness。
公开工具与终评可使用不同后端，按任务声明和校准条件验收；各部署与组合分别留证。

固定 vaBench、Analog 操作者协议和主机原生 Codex 接口继续按受影响范围回归。
保留原生工具限制；受控电路入口不表示 Agent 的其他工具被禁用。
实验前按[调用链约定](EXPERIMENT_PROTOCOL.md)核对版本、权限、预算与证据位置。
计划、已有凭据或历史成功记录不自动授权新实验。

## 1. 先定义这次要验证的行为

复用已有任务卡、Tool 规格或 issue 中的要求，不为每个小改动额外生成完整计划。
涉及新后端或跨模块变更时，补充一份简短规格：输入输出、失败语义、修改位置、验收条件和未覆盖范围。
电路规则来自专家确认的单位、端口、工艺和指标容差；缺失时明确列为待确认。

开发规格描述预期行为；实施记录描述实际改动和验证。不要把计划中的勾选项当成已经完成的证据。
先搜索现有实现、测试和讨论，保留既有公开接口和测试路径。

## 2. 对行为变更逐项做 TDD

1. **Red**：为一个关键行为写最小测试，通过公开入口调用，运行并确认因该行为尚未满足而失败。
   导入错误或缺依赖应先定位；不能把无关环境故障当作需求已被测试覆盖。
2. **Green**：实现足够满足该行为的改动，运行该测试；随后再做下一个行为。
3. **Refactor**：在测试通过后整理代码，复跑受影响测试，保留相同的可观察行为。

优先覆盖真实边界：输入验证、进程启动、超时、取消、重复提交、产物校验、结果判定。
避免仅断言私有函数调用次数或复制实现公式；构造夹具必须写明它模拟了什么。
纯文档调整只做链接、内容和 diff 检查；不要为 Markdown 措辞制造 TDD 测试。
对已有实现补测试应记为回归补充，不能倒写一段不存在的 Red 历史。

## 3. 区分测试层次

| 层次 | 内容 | 能支持的结论 |
| --- | --- | --- |
| 本地回归 | 临时目录、真实本地进程、GDS、构造 SSH/EMX 边界 | 对应代码/协议行为正确；不证明实验室可运行 |
| 服务器巡检 | 配置明确的主机与目录元数据、显式 HTTPS 探测 | 某时刻的观察；不等于性能基准或认证成功 |
| 实验室集成 | 真 SSH、获准的 EMX/Spectre、已知输入、独立结果检查 | 对应环境和任务的真实仿真闭环 |
| Agent 端到端 | 固定任务/工具/模型，真实调用与独立判定 | 模型和 Agent 在该配置下的表现 |
| 对照实验 | NFS/SSD、Agent 位置、并发或工具方案的受控比较 | 指定负载和预算内的比较结论 |

默认 CI 运行本地检查，不自动联系实验室或模型服务。外部执行按用户已授权的主机、数据和预算进行，
缺少这些信息时先完成不依赖它们的部分；不要因为已经有密钥就推断有新增付费或数据外发授权。
故障注入局限于隔离测试作业，不重启共享服务器或切断公共网络。

开源仿真器任务可先用 Bubblewrap 调用宿主机软件做快速 smoke 和排障；进入正式对照时，
同一任务固定使用经验证的 Podman 镜像、执行配置与评分脚本。两条路径是替代执行方式，
不是一次实验的前后步骤；Bubblewrap 结果不能与固定镜像结果混作同一评测条件。
执行后端由 Harness 的任务配置指定并写入运行记录，不让 Agent 为同一任务自行选择。
当前约定已用于 Analog Design Bench。VABench 的公开 EVAS Tool 已用上游 Bubblewrap
执行器完成 Agent 闭环，不能仅因它使用 Bubblewrap 就把已有结果重新标成 smoke；
改用 Podman 须另建固定镜像，并验证公开反馈、隔离边界和原评分器结果等价，作为新执行条件记录。
Spectre、EMX 等实验室软件按其许可证、工艺和服务器部署条件单独确定后端，
不假定可以放进同一镜像。跨任务统一的是预检、固定版本、公开反馈、独立终评与轨迹归档，
不是强制所有仿真器使用同一种执行后端。

## 4. 保留测试与证据

- Git 保存测试代码、匿名/构造夹具、案例规格、命令和模板；它们随功能迭代长期维护。
- 机器配置、原始日志、模型轨迹、完整仿真结果保存在部署规范指定的私有位置。
  本地回归产物可放忽略的 `runs/chips/validation/<run-id>/`；忽略规则不代替文件权限。
- 记录仓库提交与未提交改动、测试/输入版本与摘要、工具/模型版本、命令、执行环境、状态和证据路径。
- 记录 `passed`、`failed`、`blocked`、`not_run`，单列 skip/xfail 和原因；零项执行或全部跳过不是验收通过。
- 保存必要的 Red 和 Green 证据，不仅保存最终成功截图。真实结果不得用构造 fixture 填补。
- 对外分享前核查原始输出；路径、主机、prompt 和许可证信息也可能属于私有资料。

CI 的测试报告仅含本地检查；Artifacts 有保留期限，需要长期复核的结果另行归档。
不能把 GitHub artifact 上传视为对 PDK 或实验室日志的默认授权。

## 5. 如何比较“最佳方案”

先固定任务、有效输入、正确性容差、资源/费用预算、比较指标和停止条件。
访问边界、结果正确性、恢复一致性是门槛；通过后再比较耗时、成功率、资源、传输和维护成本。
先做小规模预试了解波动，再决定重复次数；记录全部计划运行与失败，不只挑选快的成功样本。
交替/随机安排可比运行次序，记录并发负载，区分首次与重复运行；不清空共享系统缓存来制造对比。
没有充分样本时不把 p95 或一次最优值当作稳定性能。真实模型输出采用结构、语义和外部状态/电路指标验收。

结论写清适用条件，例如“在这组任务、线程数、版本和网络条件下，方案 A 的中位耗时更低”。
环境或实现发生相关变化时复跑；一次通过不保证未来始终可用。

## 6. 完成交付

运行受影响的 Chips 检查和必要静态检查，检查 diff；只有跨通用边界的实际风险才扩大测试。
按实际受影响的组件选择验收范围。
按 [PR 交付规则](#delivery-and-review) 提供改动、复现命令、实际检查和未验证项，
在已有 Issue/PR 留下源码身份、下一项依赖及 [工作区交接状态](#workspace-handoff)。
文档／skill 重构检查指令触发、正文与 UI 元数据一致性、链接及目标提交中的文件可用性；
用实际任务场景核对阶段选择和范围边界。静态检查通过不等于所有 Agent 调用行为已经验证。

本 SOP 借鉴 VisionMem 的规格/实施计划分离、文件职责表、独立 E2E 入口、组件真实性标注和
结构/语义/状态断言方式；不引入其多模态运行栈或特定 Agent/第三方流程要求。
