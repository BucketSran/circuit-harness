## 1. 平台的意义

第一目标是让成员在自己的机器上取得相同版本的仓库，配置各自的实验室访问方式后，
按照同一协议完成输入准备、仿真、产物回收和结果判定。设计经验在这个平台上逐步沉淀为
任务集、可独立评测的工具和可追溯的经验，再用于改进 IC design Agent。

Harness 覆盖环境准备、任务/输入契约、执行、故障处理、观测、评测与复现证据。
目前已经实现的是执行基础及本地测试，真实实验室与第二台机器的复现尚未验收。
“拉代码即可复现”需要明确支持的主机环境、依赖版本和实验室前置条件，不能理解成自动具备
EDA 许可证、工艺数据和服务器访问权。当前执行器要求 POSIX，本机 macOS 和 CI Linux 已测；
Windows 原生、WSL 和其他实验室环境均未验收。

首条业务链路仍为 **JSON → GDS → SSH → 实验室 EMX → 下载日志/结果**。
当前几何 JSON 只是演示格式。最终 JSON 协议、工艺和端口设置由真实案例确定。
本地 Icarus 用于进程管理自测，不是当前研究主线。

## 2. 平台上的四条建设方向

| 方向 | 产出 | 判断是否有效 |
| --- | --- | --- |
| 自建任务集与数据集 | 有版本、约束、参考结果和独立判定规则的电路任务 | 新成员能复现，已知正确/错误案例可以被区分 |
| 可迁移的 Tools | 明确输入输出、执行边界、失败语义和测试夹具的能力模块 | 脱离 Agent 也能直接测试，同一工具可由不同 runtime 调用 |
| Agent / Tools 联合实验 | Pi 为主要实验入口，Codex 作辅助对照；记录实际工具集合和调用证据 | 控制模型、预算、任务、工具与流程后比较收益 |
| 经验与 Memory | 带来源、适用条件和验证状态的知识；受控检索与反馈 | 在独立任务上比较 memory-off/on，而非仅统计记忆条数 |

Skills 可以承载操作说明和专家指导；评测中的实际能力应尽量通过显式 Tool 契约执行。
Tool 可以含算法、外部软件，也可以调用模型；后一种必须记录内部模型、调用和成本，
不能把隐藏的内部推理全部归因于外层 Agent。薄适配层接入 MCP，领域实现保留直接调用入口。

## 3. 标准化 Harness 的第一轮验收

先用一个固定案例完成下面的闭环，再扩充 benchmark：

1. **部署前检查**：检查本机依赖、SSH 登录、远端 Python、EMX 命令、工艺/端口设置和许可证。
   报告缺哪一项；不靠遇到错误后不断改命令来猜环境。统一 preflight 命令尚待实现。
2. **无模型基线**：用固定输入直接调用工具，得到专家认可的真实 GDS、EMX 日志及结果。
3. **结果判定**：明确运行成功、结果有效、设计达标三个判断；缺失证据表示不可评。
4. **运行证据**：记录代码/任务/工具版本、输入及配置摘要、远端 job ID、日志、产物哈希和指标。
   现有代码只覆盖其中部分内容，统一跨机器 run manifest 与指标报告还待实现。
5. **故障恢复**：真实连接中断、恢复下载及同一 job 重连有证据；不能因丢失回复再启动一份仿真。
6. **第二位成员复现**：在另一台机器按文档独立完成同一案例，比较产物结构与指标容差。
   如果工具结果有数值波动，采用专家给定的容差，不强求跨环境二进制完全一致。
7. **模型入口**：在前述基线成立后接 Pi，核对参数、反馈、停止行为和完整调用关联，再加入 Codex。

无需等平台完全通用才收集任务卡和专家经验；它们可以同步整理，但进入正式评测前必须完成验收。

## 4. 任务与数据的统一入口

[examples/chips/benchmarks/](../../examples/chips/benchmarks/README.md) 是任务定义与登记的唯一入口。
已有 RC 与 VABench 任务登记；VABench 复用外部固定 release 的任务契约和原评分器。
当前优先完善这一条可观察主线，尚未建立通用 Chips benchmark loader。
当前 [EMX tasks.jsonl](../../examples/chips/emx/tasks.jsonl) 仍是 smoke 输入，不把它计作电路 benchmark。

每个任务至少明确：输入、允许修改的变量和范围、固定条件、工具要求、预算、结果有效性规则、
目标指标、单位/容差、专家参考结果、开发/测试划分及版本。运行错误与设计不达标分别统计。

目录内保存可共享的小样例和数据来源清单；大型数据、受限工艺和运行产物通过本地配置及摘要引用。
规范化构建复用现有 data_preprocess 的 public/private + manifest 机制；未来 Chips 适配落在
`alphaapollo/data_preprocess/chips/`。最终评分代码拟落在 `alphaapollo/common/grader/chips/`，
必须保持 Grader 的确定性契约；EDA 执行与结果解析由执行层产生受信证据，不在纯评分接口暗中启动仿真。
这些路径尚未实现，具体接口须以第一个真实任务为依据。

Robotics 的任务、Episode、Direct/Agent/Workflow 对照和独立成功判定可作设计参考。
Chips 的长时仿真、工艺约束、连续指标与容差需要自己的协议，不逐项照搬机器人控制语义。

## 5. 以 Pi 为主要工具实验入口

源码已有 [PiSession](../../alphaapollo/reasoning/runtime/external/agents/pi.py)、
[Pi MCP extension](../../alphaapollo/reasoning/runtime/external/bridge/pi_extension.ts) 和
[外部轨迹适配](../../alphaapollo/reasoning/runtime/external_agent_runtime.py)。
Pi 是执行循环，具体模型另行配置。[VABench 专用入口](VABENCH_AGENT.md) 已接通四个公开工具、
Pi 0.87.0、原评分器及归档，并通过脚本模型响应集成测试及 GLM 5.3 Flash 的 `v4-001` 单任务真实回合。
工具能力收益和跨任务成功率尚未验证；
原 EMX smoke 示例仍保留 Codex 配置。

Pi 的桥接模式要求 `no_builtin` 或 `allowlist`；受控实验应核实最终实际可见工具集合。
原生 Codex 仍有自己的执行工具，授予一个 MCP 工具不等于关闭所有内建工具。
Codex 可用于实用性对照；若控制条件不等价，应报告差异，不能把结果全部归因于工具设计。
保留的基线还有 `codex_via_pi` 适配，但同样需要核对实际 provider/model/CLI 和工具限制后使用。

### 调用观测的边界

Pi 的 JSON 事件可提供工具名、参数、返回内容、错误及 provider 可用的 usage；外部 runtime 将其投影到轨迹。
这不是对所有进程和所有模型请求的通用拦截器：单次 bash 内部的 EDA 步骤需要执行器自行记录，
没有暴露的 usage、重试次数或模型内部推理不得推测为已测量。

当前 Pi extension 没有把 Pi 原生 toolCallId 原样透传给 MCP；
[通用 MCP 服务](../../alphaapollo/common/execution/tools/mcp.py) 创建自己的调用 ID。
Chips 会记录收到的调用 ID，并返回 run_id/job_id，但跨层关联必须通过真实运行验收，
不能假设所有 ID 天然相同。标准报告应能把模型调用、工具执行、仿真 job 与产物明确关联。

### 控制变量的实验顺序

| 实验 | 固定 | 改变 | 目的 |
| --- | --- | --- | --- |
| 工具直接回放 | 输入、软件环境与目标 | 工具实现版本 | 测工具正确性、稳定性与性能 |
| 工具接口对照 | 同一 Pi、模型、任务、预算、memory 关闭 | 工具粒度、说明、反馈或暴露集合，每次一项 | 测工具是否更易用且有实际收益 |
| 模型对照 | runtime、工具、任务、预算 | 模型/采样设置 | 测模型差异 |
| Agent 流程对照 | 尽可能相同的模型、工具、任务、预算 | 流程或 runtime | 测调度/上下文/停止策略；记录无法消除的差异 |
| 经验对照 | 模型、工具、任务与预算 | 冻结的经验快照是否可用 | 测 memory 的泛化收益与检索成本 |

工具数量不是优化目标。比较必要能力是否齐全、错误选择/参数错误、冗余调用、成功率和总成本。
当前一个 `emx_simulate` 封装整个链路；是否拆分转换、仿真、指标解析，应由任务需求和对照结果决定。
复合工具可减少决策负担，细粒度工具可增加组合灵活性，二者都需要实验。

任务难度和模型能力表必须记录任务族、版本、工具/流程条件、样本数及不确定性。
多模型自动路由放在稳定任务与能力数据之后，不作为第一阶段平台的前置条件。

## 6. 经验库与 Memory

从现在就整理专家经验：适用的电路/工艺/软件版本、现象、处理方法、原始 run/产物来源、
成功与反例、专家确认状态。运行日志是原始证据，经过核实的经验才进入可复用集合。

代码已有 [memory 接口与作用域](../../alphaapollo/evolving/memory/interface.py)、working/persistent 存储，
以及 [Workflow memory adapter](../../alphaapollo/workflows/memory/adapter.py)。
目前没有 Chips adapter。`MemoryScope.allows` 要求 namespace 和 task_id 一致；持久化只放宽 run，
不会自动让新任务读到其他任务经验。跨任务经验库还需要适用条件、检索范围和审核/晋升策略，
不能通过把所有任务都改为相同 ID 来绕过隔离。

按两条通道建设：

- **任务内 memory**：保留本次任务已试参数、已运行 job、结果和失败原因，减少重复劳动。
- **跨任务经验库**：从开发任务和专家材料提炼经验，按任务族/工艺版本适配检索，保留来源和撤销能力。

先做专家审核的经验快照和只读检索，再评估自动写入。测试前冻结快照，最终评测标签/答案不写回
当前测试使用的记忆；在线学习另做协议，明确任务顺序和允许反馈。效果改善要在独立任务上验证。
初期的“进化”指工具/流程/可检索经验的版本迭代，不等于自动更新模型权重或保证效果单调提升。

## 7. 协作与阶段顺序

开发集成分支为公开仓库 `BucketSran/circuit-harness` 的 `main`。
旧参考分支已退役，材料保留在私有历史备份；历史来源提交见[分支说明](PHASE1_HARNESS.md#分支与协作)。
专家及其 Agent 在 Chips 范围内提交任务、工具规范和实现；功能分支通过 PR 向 `main` 集成。
邀请按用户要求暂缓。上游只读，不向上游创建分支/PR；参考领域的运行测试不属于 Chips 验收。

| 阶段 | 可检查的完成条件 |
| --- | --- |
| A：平台可复现 | 一个真实任务、统一部署检查、有效结果判定、恢复证据、第二台机器复现 |
| B：任务与工具基线 | 一个小型任务集、独立评测、工具直接回放；Pi 固定模型闭环 |
| C：工具与 Agent 研究 | 工具实现/接口/集合、模型与流程的配对对照；Codex 辅助验证 |
| D：经验与持续改进 | 可追溯经验快照、Chips memory 接入、独立任务上的 memory-off/on 评测 |

下一项实现应收敛为“实验室 preflight + 一个真实 EMX 案例 + 第二位成员复现说明”。
尚缺真实布局/生成规则、可运行的 EMX 命令、工艺与端口配置，以及专家认可的输出。
任务卡和工具规范现在即可由专家与其 Agent 补充，具体落点见协作指南。
