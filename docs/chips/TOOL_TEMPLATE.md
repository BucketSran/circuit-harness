# Chips Tool 规格模板

用途：先把可评测的能力说清楚，再由协作 Agent 在对应代码位置实现。
当前只有 `emx_simulate` 已接入；本模板不注册或启用任何新工具。

## 能力与边界

- 名称 / 版本 / 负责人：
- 解决什么电路问题；哪些任务需要它：
- 单一操作还是复合链路；是否内部调用模型/子 Agent：
- 对外稳定的输入与输出；与 Pi/Codex 无关的直接调用入口：
- 使用现有工具是否足够；新工具或拆分接口的可检验理由：

## 输入、配置和结果

- 模型可填写的参数：类型、单位、范围、默认值和非法输入示例：
- 操作者固定的配置：软件、工艺、服务器、超时与资源限制：
- 输出指标、原始产物、日志引用及结果有效性规则：
- 输入/配置/软件版本如何识别；哪些依赖无法完整追溯：
- 如果调用模型：内部模型、提示版本、次数与可用成本证据：

## 错误、生命周期和观测

- 非法输入 / 工具依赖问题 / 执行故障 / 设计不达标 / 不可评分别如何表达：
- 哪些错误可重试、哪些必须停止；最多几次、总预算多少：
- 重试或恢复是否可能重复启动作业；如何识别已有结果：
- 取消、超时和进程清理；无法确认远端状态时如何报告：
- 模型调用、MCP 调用、run/job 和产物的关联证据：
- 原始结果与返回模型的摘要有何区别；摘要丢失了哪些信息：

## 验收与研究

- 固定输入直接调用的成功、设计失败、执行故障样例及预期输出：
- 是否经过真实软件验收、第二位成员复现：
- 与旧版本比较时固定什么，改变什么：
- 正确率、稳定性、无效/冗余调用、时延与成本如何测量：
- 模型和 runtime 是否固定、memory 是否关闭、通用 shell 是否构成旁路：
- 模块迁移到另一个 Agent 时需要哪些依赖与适配：

## 代码落点

领域实现优先放 `alphaapollo/common/execution/chips/`；模型接口放
`alphaapollo/common/execution/tools/chips.py`，多个真实工具出现后按职责拆分。
复用既有 MCP/ToolCatalog 接口。相关测试放到对应的 `tests/common/execution/` 或 `tests/workflows/`。
完整职责表见 [CONTRIBUTING.md](CONTRIBUTING.md)。
